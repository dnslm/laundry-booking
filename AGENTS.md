## 1. О проекте

Система бронирования стиральных машин в общежитии. Учебный командный проект по веб-разработке: 4 человека, около месяца на разработку, затем подготовка к защите. Защита идёт с локальным запуском, публичный деплой не нужен.

Реальная проблема: запись на стирку неудобна, а часть машин часто сломана. Заказчик по сюжету проекта: студсовет общежития.

### Конечный вид (4 экрана)

1. `/login` и `/register`: вход и регистрация.
2. `/booking`: сетка слотов. Выбор дня, строки это машинки, ячейки это слоты со статусами «свободно», «занято», «моя», «сломана».
3. `/my`: «Мои брони» со списком и кнопкой отмены.
4. `/admin`: список машинок со статусом и переключателем «работает/сломана», все брони с кнопкой «отменить».

### Критерий готовности MVP: демо-сценарий

Проект готов, когда этот сценарий проходит на настоящем бэкенде без ошибок:

1. Студент регистрируется и входит.
2. Выбирает день и машинку, бронирует слот и видит его в «Моих бронях».
3. Другой пользователь пытается занять тот же слот и получает отказ.
4. Студент отменяет бронь, слот снова свободен.
5. Админ отмечает машинку сломанной, её слоты пропадают из сетки.
6. Админ видит все брони и может отменить любую.

### Объём работ

- Сейчас: только стирка в одном общежитии (4 машинки, по одной на этаж). Модель данных сразу поддерживает несколько общежитий через `dorm_id`.
- Позже и только по решению команды: коворкинги, check-in, рейтинг надёжности, очередь ожидания, уведомления.
- Не делать без отдельной задачи: платежи, внешние интеграции, деплой.

### Предметная область

- Слоты считаются из настроек общежития и в БД не хранятся. Бронировать можно с 09:00 до 23:00, перерыв 13:00-15:00 брать нельзя.
- Длина слота лежит в настройках общежития и ещё обсуждается, поэтому не хардкодь её.
- Вход по логину и паролю. Имя, фамилия, общежитие, номер комнаты и контакт для связи это поля профиля. В комнате могут жить люди с одинаковыми именами, поэтому имя и фамилия обязательны.
- Роли: `student` и `admin` (студсовет).
- Машинка со статусом `broken` не показывает слоты для брони.
- Двойную бронь запрещает ограничение в БД `UNIQUE (machine_id, date, slot_start)` вместе с транзакцией на сервере, а не проверка на клиенте.
- Правила: нельзя бронировать прошлое, есть окно записи вперёд, лимит броней на человека в неделю, один человек не занимает два слота одновременно на разных машинках, отмена не позже чем за N минут до начала слота.
- Статусы брони на этапе изюминок: `booked`, `checked_in`, `finished`, `no_show`, `cancelled`.

### Открытые решения

Агент не принимает их молча. Предложи варианты с плюсами и минусами и дождись решения человека. В скобках то, что предложено, но не утверждено.

- СУБД: SQLite или PostgreSQL (предложено SQLite). Критерии по БД от преподавателя ещё не пришли.
- ORM: Prisma или сырой SQL (предложена Prisma). Не пиши код Prisma по памяти: API менялось между версиями, сверяйся с документацией установленной версии или с установленным skill.
- Аутентификация: решение для фронтенда принято — JWT в `localStorage`. Бэкенд должен это подтвердить; риск XSS принят осознанно.
- Длина слота: 2 часа или 30 минут (предложено 30 минут и кнопка «завершил»).
- Числа правил (предложено: 7 дней вперёд, 3 брони в неделю, отмена за час).
- Идентификатор для входа: решено — логин.
- Как студсовет получает права админа (предложено: заранее созданный аккаунт через seed).

## 3. Команды

Команды выполняются из корня репозитория в Git Bash.

```bash
yarn install
yarn lint            # проверка ESLint
yarn lint:fix        # ESLint с автоисправлением
yarn format          # Prettier
yarn format:check    # проверка форматирования, то же делает CI
yarn types           # typecheck во всех пакетах
yarn tests           # тесты во всех пакетах
yarn build:all       # сборка всех пакетов
yarn workspace backend <скрипт>
yarn workspace frontend <скрипт>
```

Каждый пакет определяет скрипты `typecheck`, `test` и `build`. Корневые `types`, `tests` и `build:all` запускают их везде, где они есть.

Прежде чем сказать «готово», прогони `yarn lint`, `yarn format:check`, `yarn types` и `yarn tests`.

### Правила фронтенда

- HTML-файл один. Страницы это React-компоненты, роутинг в `App.tsx`.
- Страница это папка `pages/<Name>/` с файлами `<Name>.tsx` и `<Name>.module.css`. Большую страницу делим на соседние `.tsx`.
- Страницы не ходят в сеть и не импортируют `mocks.ts` напрямую, только функции из `api/`. Пока бэкенда нет, `api/*` возвращает данные из `mocks.ts` с небольшой задержкой. Когда бэкенд готов, меняется только содержимое функций.
- Типы в `types/index.ts` совпадают с `docs/api.md`.
- В заглушки закладывай плохие случаи: слот занят, лимит исчерпан, пустой список, ошибка сервера.
- Страницы и компоненты называются в `PascalCase`, остальные файлы в `camelCase`.
- Общий компонент принадлежит тому, кто его создал. Использовать его можно всем.
- Визуальный стиль обязателен для всех страниц: см. раздел 11.

## 5. Общие правила для всех агентов

### Старт сессии

1. Выясни у человека его роль (раздел 6) и задачу. Если не сказано, спроси.
2. Если задача касается API, прочитай `docs/api.md`.
3. Сначала пришли план: какие файлы создашь или изменишь и зачем. Код пиши после согласия человека.
4. Работай маленькими шагами и после каждого говори, как проверить результат.

### Git и процесс

- Не коммить в `main`, не мерджи и не пушь без явной просьбы человека. Работай в ветке `feat/...`, `fix/...`, `docs/...` или `chore/...`.
- Одна задача, одна ветка, один небольшой PR. Заголовок PR оформляй как сообщение коммита: `feat: добавил проверку пересечения слотов`.
- Не используй `git push --force`, `git reset --hard`, `git clean -fd` и другие разрушающие команды без явного подтверждения.
- Не правь старые миграции. Новое изменение схемы это новая миграция.

### Качество и безопасность

- Контракт API сначала записывается в `docs/api.md`, потом пишется код.
- Всё, что защищает данные (пересечения броней, лимиты, роли), проверяется на сервере. Клиенту не доверяем.
- Пароли хранятся только как хэш (bcrypt), в логи пароли и токены не попадают.
- Вход в API валидируется через zod. Запросы к БД параметризованы или идут через ORM.
- Секреты, `.env` и ключи не коммитятся. В репозитории только `.env.example`.
- Реальные данные студентов (имена, комнаты) в репозиторий не попадают. В seed и тестах только вымышленные люди. Реальные машинки и этажи можно.
- Новые зависимости добавляй только при необходимости и объясняй причину в описании PR.
- Не раздувай объём. Проверь по разделу 8, что задача относится к текущему этапу.

### Стиль

- Идентификаторы и комментарии в коде на английском. Документация, коммиты, PR и тексты интерфейса на русском.
- Если человек просит объяснить изменение, объясняй простыми словами и по шагам, без лишнего жаргона.

### Когда остановиться и спросить человека

- Задача требует изменений вне зоны человека (раздел 6).
- Нужно менять схему БД или добавлять зависимость.
- Затронуто что-то из открытых решений.
- Правило предметной области неясно или противоречит другому.
- Нужна разрушающая git-команда.
- Решение влияет на безопасность.

## 7. Агенты и субагенты

Оркестратор разбирает задачу и раздаёт её специалистам, специалисты работают только в своей зоне, ревьюер проверяет результат. Включай агентов по мере надобности: для старта хватит `orchestrator`, `db-schema`, `booking-core` и `code-reviewer`.

### `orchestrator`

- **Зона:** вся картина репозитория, сам почти не пишет код.
- **Делает:** разбирает задачу на подзадачи, выбирает субагентов, следит за этапом и объёмом, собирает результат и формулирует итог человеку.
- **Не делает:** большие куски кода, схему БД, открытые решения.

### `api-contract`

- **Зона:** `docs/api.md`, типы в `frontend/src/types/index.ts` (по согласованию с ролью 3).
- **Делает:** проектирует эндпоинты, тела запросов и ответов, коды ошибок и права для `student` и `admin` так, чтобы фронтенд мог работать на заглушках.
- **Не делает:** реализацию, правки контракта после начала работы над фичей без согласования обеих сторон.

### `db-schema`

- **Зона:** `backend/prisma/schema.prisma` и миграции.
- **Делает:** модель данных (`dorms`, `machines`, `users`, `bookings`), ограничения и индексы, включая `UNIQUE` на слот.
- **Не делает:** не мерджит схему без одобрения роли 1, не правит старые миграции. Каждое изменение схемы это маленький отдельный PR, который мерджится первым.

### `booking-core`

- **Зона:** `backend/src/modules/bookings`, `backend/src/lib`.
- **Делает:** расчёт слотов из настроек общежития, создание и отмена брони, защита от гонок через транзакции и ограничение БД, вызов функций правил из `rules-engine`.
- **Не делает:** не меняет схему и авторизацию, не добавляет check-in и рейтинг до этапа 4.

### `rules-engine`

- **Зона:** `backend/src/modules/rules`.
- **Делает:** правила бронирования в виде отдельных чистых функций с тестами Vitest: прошлое, окно вперёд, недельный лимит, одновременные брони, срок отмены. Числа берёт из настроек общежития.
- **Не делает:** не обращается к БД напрямую, не меняет схему.

### `auth-admin`

- **Зона:** `backend/src/modules/auth`, `users`, `machines`, `admin`, `backend/src/middleware`.
- **Делает:** регистрацию и вход, хэширование bcrypt, токены или сессии, проверки `requireAuth` и `requireRole`, админ-API: статус машинок, все брони, отмена любой брони.
- **Не делает:** не меняет логику бронирования, не выбирает JWT или сессии без человека.

### `frontend-booking`

- **Зона:** `frontend/src` кроме страниц и компонентов роли 4.
- **Делает:** каркас Vite, роутинг, API-клиент и заглушки, `AuthContext`, `Layout`, страницы `BookingPage` и `MyBookingsPage`, состояния загрузки, ошибки и пустые экраны, переход с заглушек на настоящий бэкенд.
- **Не делает:** не меняет контракт API, не считает серверные проверки достаточной защитой на клиенте.

### `frontend-pages`

- **Зона:** `pages/LoginPage`, `RegisterPage`, `AdminPage`, `NotFoundPage`, `components/Button`, `FormField`.
- **Делает:** формы входа и регистрации с проверкой полей и сообщениями об ошибках сервера, админку (машинки со статусом, все брони с отменой), общие компоненты форм.
- **Не делает:** не меняет контракт API, не трогает каркас и сетку слотов.

### `test-writer`

- **Зона:** `**/*.test.ts`, `**/*.test.tsx`.
- **Делает:** unit- и интеграционные тесты на Vitest: пересечения слотов, лимиты, роли, параллельные запросы.
- **Не делает:** не правит прикладной код ради прохождения теста, не удаляет падающие тесты. Найденные баги передаёт профильному агенту с описанием воспроизведения.

### `code-reviewer`

- **Зона:** только чтение, код не правит.
- **Делает:** проверяет изменения по чек-листу: соответствие задаче и этапу, гонки при бронировании, серверные проверки и роли, секреты и логи, тесты, синхронизацию с `docs/api.md`, безопасность миграций, размер PR. Отчёт делит на блокирующие замечания, предложения и мелочи.
- **Не делает:** не одобряет PR вместо человека. Апрув ставит человек.

### `devops-ci`

- **Зона:** `.github/**`, `.husky/**`, корневые конфиги, `package.json`, `eslint.config.mjs`, `.prettierrc.json`, `.nvmrc`.
- **Делает:** поддерживает CI, хуки, линтеры, зависимости и скрипты, разбирает падения проверки `check`.
- **Не делает:** не ослабляет правила линтера, чтобы «починить» CI, не обновляет TypeScript до 7, не меняет код приложений.

### `docs-demo`

- **Зона:** `README.md`, `docs/data.md`, `docs/test-plan.md`, `backend/prisma/seed.ts`, прочие файлы в `docs/` кроме `docs/api.md`.
- **Делает:** README, описание реальных данных об общежитии, seed с реальными машинками и вымышленными людьми, тест-план для ручной проверки, сценарий демо, структуру слайдов, вероятные вопросы преподавателя.
- **Не делает:** не описывает то, чего в проекте ещё нет, не меняет схему БД.

### `git-helper`

- **Зона:** только объяснения и подсказки, репозиторий меняет по просьбе человека.
- **Делает:** помогает с ветками, подтягиванием `main`, конфликтами и оформлением PR. Объясняет каждую команду и её последствия, сначала показывает `git status` и `git diff`.
- **Не делает:** не выполняет разрушающие команды без явного подтверждения, не решает конфликты в `schema.prisma` и миграциях за человека.

### Агенты следующих этапов

Включаются только после заморозки ядра и по решению команды.

- `checkin-rating`: check-in, статусы `no_show` и `finished`, простой рейтинг надёжности.
- `waitlist-notify`: очередь ожидания и уведомления.

## 8. Этапы

Текущий этап: **1. Основа и прототип страниц на заглушках** (обновляйте строку вручную).

1. **Основа.** Репозиторий (готов), каркас бэкенда, схема БД, контракт API, каркас фронтенда и все страницы на заглушках, регистрация и вход на бэкенде.
2. **Ядро.** Слоты, создание и отмена брони, лимиты, защита от пересечений, тесты. Сетка слотов и «Мои брони» подключаются к настоящему бэкенду.
3. **Админка и доводка.** Статус машинок, просмотр и отмена броней, обработка ошибок, адаптивность. В конце заморозка фич.
4. **Стабилизация.** Тесты, документация, демо, слайды. Изюминки (check-in, рейтинг) только если ядро надёжно.

Не реализуй возможности следующих этапов, пока человек не попросил.

## 9. Протокол передачи результата

2. Список затронутых файлов.
3. Как проверить (команды и сценарий).
4. Открытые вопросы к человеку.
5. Что не сделано и почему.

## 10. Ревью чужого кода

Файл подходит как контекст для другой ИИ-модели, но одного файла мало: к нему нужно приложить задачу и диф. Порядок:

1. Прочитай этот файл целиком и раздел 0.
2. Возьми у человека ветку и задачу. Посмотри изменения: `git fetch origin && git diff origin/main...HEAD`.
3. Ничего не меняй, пока человек не попросил. Ревью — только чтение.
4. Проверь код по чек-листу ниже.
5. Верни отчёт: блокеры, предложения, мелочи. Ссылки в формате `путь:строка`.

### Чек-лист

- Задача и объём: изменения решают задачу и не тащат следующий этап.
- Зоны: не сломаны ли чужие файлы, нет ли правок схемы без владельца.
- Контракт: если затронут API, обновлён `docs/api.md`, типы совпадают с контрактом.
- Сервер: права, лимиты, пересечения и отмена проверяются на сервере, а не только на клиенте.
- Гонки: создание брони в транзакции, ограничение `UNIQUE (machine_id, date, slot_start)` на месте.
- Безопасность: bcrypt, нет секретов и токенов в логах, zod на входе, параметризованные запросы.
- Фронтенд: страницы ходят только в `api/`, нет UI-библиотек, стили в CSS Modules, есть состояния загрузки, ошибки и пустого списка.
- Доступность: label, клавиатура, видимый фокус, ошибки с `aria`.
- Тесты: новые правила покрыты, старые тесты не удалены и не ослаблены.
- Миграции: новая миграция вместо правки старой.
- Размер: PR можно отревьюить за один заход.

### Готовый промпт другой модели

```text
Прочитай AGENTS.md целиком, особенно разделы 0, 5 и 10.
Задача: <ссылка или описание>. Ветка: <ветка>. Диф: git diff origin/main...HEAD.
Проверь изменения по чек-листу раздела 10. Код не меняй.
Верни: блокеры, предложения, мелочи. Для каждой находки — файл:строка и почему это важно.
Если чего-то не хватает для проверки, задай вопрос, а не догадывайся.
```

Не прикладывай к промпту `.env`, `node_modules`, токены и реальные данные студентов.

## 11. Визуальный стиль

Решение владельца страниц входа от 26.11.2026. Распространяется на все страницы, не только на вход и регистрацию.

### Направление

- Основа — фирменные цвета НИУ ВШЭ, но не копия сайта Вышки.
- Ощущение: небольшой локальный сайт середины 2010-х, в духе RateYourMusic. Плотно, утилитарно, по делу.
- Не «нейрослоп»: без фиолетовых градиентов, стекла, размытий, огромных скруглений, парящих карточек, эмодзи-иконок, анимаций ради анимации и одинаковых SaaS-лендингов.
- Интерфейс выглядит как инструмент, а не как промо-страница. Никаких маркетинговых заголовков на пол-экрана.

### Цвета

| Токен             | Значение  | Где использовать                 |
| ----------------- | --------- | -------------------------------- |
| `--color-primary` | `#0F2D69` | основной синий: кнопки, мастак   |
| `--color-accent`  | `#234B9B` | ссылки, фокус, активные элементы |
| `--color-bg`      | `#F0F0F0` | фон страницы                     |
| `--color-panel`   | `#FFFFFF` | панели и поля                    |
| `--color-text`    | `#1A1A1A` | основной текст                   |
| `--color-muted`   | `#5A5A5A` | подсказки и второстепенный текст |
| `--color-border`  | `#C9C9C9` | рамки, разделители               |
| `--color-error`   | `#A31F1F` | ошибки                           |

- Все цвета только через CSS-переменные в `index.css`. В модулях не хардкодить.
- Логотип и шрифты ВШЭ не скачиваем и не коммитим: они принадлежат университету. Допустимы текстовое упоминание и цвета.

### Типографика

- Одно семейство на весь интерфейс, без пар «заголовочный + текстовый».
- Основной шрифт: **PT Sans** (ParaType, SIL OFL 1.1). Русский гротеск 2009 года, хорошо ложится на локальный сайт и не выглядит как современный SaaS.
- Подключение: локально через `@fontsource/pt-sans`, только кириллица и латиница, веса 400 и 700. Без Google Fonts CDN и внешних запросов.
- Запасной стек на случай сбоя загрузки: `"PT Sans", "Segoe UI", Tahoma, Arial, sans-serif`. Он не определяет внешний вид, а только страхует.
- При коммите шрифтовых файлов рядом кладём `OFL.txt` или ссылку на пакет с лицензией.
- Если команда забракует PT Sans, замена — **IBM Plex Sans** (OFL 1.1) тем же способом. Оба варианта не смешивать.
- HSE Sans не используем: проприетарный шрифт университета.
- Базовый размер 14px, межстрочный 1.45. Заголовки 18–24px, без гигантских display-шрифтов.
- Ссылки синие и подчёркнутые.
- Числа и время с `font-variant-numeric: tabular-nums`, чтобы колонки не дёргались.

### Формы и элементы

- Прямоугольные кнопки и поля, радиус не больше 2px.
- Рамки 1px, фокус 2px сплошной синий и видимый с клавиатуры.
- Никаких теней, градиентов, glassmorphism, blur, pill-кнопок и иконок-эмодзи.
- Отступы по сетке 4px. Формы компактные, но не тесные.
- Ошибки — тёмно-красный текст и рамка, без агрессивной заливки на весь экран.
- Загрузка — текстовая или простая полоса, без прыгающих скелетонов.

### Композиция

- Контент по центру, максимальная ширина 1000–1100px.
- Страницы входа: две колонки на десктопе (короткий текст и панель формы), одна колонка на телефоне.
- На телефоне всё читается с 320px, горизонтальной прокрутки нет.
- Пустые состояния и ошибки — обычным текстом, без иллюстраций.

### Запрещено

- UI-библиотеки, иконочные шрифты, внешние CSS-фреймворки.
- Скачивать и коммитить шрифты и логотипы ВШЭ.
- Подключать шрифты с внешних CDN и смешивать два семейства.
- Генерировать декоративные картинки и «AI-иллюстрации».
- Тёмная тема, если её не попросили отдельно.
- Анимации дольше 150–200 мс; при `prefers-reduced-motion` отключать.
